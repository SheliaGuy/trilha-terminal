# 06 · Kubernetes com k3s

**Tempo:** 2,5 dias · **Saída:** a app roda num cluster Kubernetes de verdade, com 2 réplicas, configuração externa e health checks. E você sabe descobrir por que um pod não sobe.

O **k3s** é um Kubernetes completo e certificado, empacotado num binário só. Ele é leve o suficiente para rodar no seu notebook. O que você aprende aqui vale para EKS, AKS, GKE e OpenShift.

## Você consegue...

- [ ] explicar Pod, Deployment, Service, ConfigMap, Secret e Namespace com as suas palavras
- [ ] aplicar manifests e acompanhar um rollout
- [ ] ler `kubectl describe` e os Events para achar a causa de um problema
- [ ] ver logs e entrar num pod

## 1. Instalar o k3s

Pré-requisito: systemd ativo (módulo 00, passo 5).

```bash
curl -sfL https://get.k3s.io | sh -s - --write-kubeconfig-mode 644 --disable traefik
sudo systemctl status k3s        # active (running)
mkdir -p ~/.kube && cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
kubectl get nodes                # STATUS Ready
```

- `--disable traefik` desliga o ingress controller que vem por padrão. Não vamos usar e ele come RAM.
- O k3s já instala o `kubectl`.
- Para desligar o k3s quando não estiver estudando: `sudo systemctl stop k3s`. Para religar: `start`.

??? tip "Autocomplete do kubectl (recomendado)"
    ```bash
    echo 'source <(kubectl completion bash)' >> ~/.bashrc
    echo 'alias k=kubectl' >> ~/.bashrc
    echo 'complete -o default -F __start_kubectl k' >> ~/.bashrc
    source ~/.bashrc
    ```

## 2. Os objetos que importam

```text
                   Service "app" (IP estável + DNS: app.trilha.svc)
                         │ escolhe os pods pelo label app=app
         ┌───────────────┴───────────────┐
      Pod app-7f9..-abc            Pod app-7f9..-xyz      ◄── criados e recriados pelo
         │                               │                     Deployment "app" (replicas: 2)
   env ◄─┴─ ConfigMap "app" (config)     │
       ◄─── Secret "db" (senha, URL do banco)
```

| Objeto | Pra quê |
|---|---|
| **Pod** | 1+ containers que rodam juntos. Mortal: morreu, outro nasce com outro nome e outro IP |
| **Deployment** | Garante N réplicas de um Pod e faz rollout e rollback de versões |
| **Service** | Nome e IP estáveis na frente dos pods. Também balanceia a carga |
| **ConfigMap** | Configuração não secreta (versão, porta, flags) |
| **Secret** | Configuração sensível. É só base64, **não** é criptografia |
| **Namespace** | Separação lógica dentro do cluster (`trilha`, `trilha-debug`) |

Você quase nunca cria um Pod direto: cria um **Deployment**, e ele cuida dos Pods.

## 3. kubectl essencial

```bash
kubectl get pods -n trilha                  # -A = todos os namespaces; -o wide = mais colunas
kubectl get deploy,svc,cm,secret -n trilha
kubectl describe pod NOME -n trilha         # ← o comando de debug nº 1: leia os Events no fim
kubectl logs NOME -n trilha                 # -f acompanha; --previous mostra o container que morreu
kubectl logs deploy/app -n trilha           # logs de um pod qualquer do deployment
kubectl exec -it NOME -n trilha -- sh       # entra no pod
kubectl apply -f arquivo.yaml               # cria ou atualiza (declarativo)
kubectl delete -f arquivo.yaml
kubectl get events -n trilha --sort-by=.lastTimestamp
kubectl explain deployment.spec.template.spec.containers   # documentação do campo, no terminal
```

Cansou do `-n trilha`? Use `kubectl config set-context --current --namespace=trilha`.

## 4. A imagem local precisa entrar no k3s

!!! danger "O erro nº 1 deste módulo"
    O k3s **não** usa o Docker. Ele tem o próprio runtime, o containerd. A imagem que você buildou com `docker build` **não existe** para o cluster, e o pod fica em `ErrImagePull` ou `ImagePullBackOff` tentando baixar do Docker Hub.

```bash
cd ~/dev/trilha-terminal/projeto
docker build -t trilha-app:0.1.0 .
docker save trilha-app:0.1.0 | sudo k3s ctr images import -
sudo k3s crictl images | grep trilha-app       # confirme que entrou
```

No manifest, use a **mesma tag**, com `imagePullPolicy: IfNotPresent`. Assim o k3s usa a imagem local e não tenta baixar. **Cada build novo exige um import novo.** Mudou o código? Gere uma tag nova (`0.1.1`), importe e atualize o manifest.

## 5. Os manifests do projeto

Crie a pasta `projeto/k8s/` com estes arquivos. Os prefixos numéricos garantem a ordem do `apply`:

| Arquivo | Conteúdo |
|---|---|
| `00-namespace.yaml` | Namespace `trilha` |
| `10-db.yaml` | Secret `db` + Deployment `db` (postgres:17-alpine) + Service `db` (porta 5432) |
| `20-app.yaml` | ConfigMap `app` + Deployment `app` + Service `app` (porta 80 → 3000) |

Um exemplo de Deployment para você entender a estrutura. **Não é o da app**: adapte.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: exemplo
  namespace: trilha
spec:
  replicas: 2
  selector:
    matchLabels:
      app: exemplo            # ← tem que bater com o label do template
  template:
    metadata:
      labels:
        app: exemplo          # ← o Service também seleciona por este label
    spec:
      containers:
        - name: exemplo
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
          envFrom:
            - configMapRef:
                name: exemplo          # todas as chaves do ConfigMap viram variáveis
          env:
            - name: SENHA
              valueFrom:
                secretKeyRef:
                  name: exemplo
                  key: SENHA           # uma chave específica do Secret
          readinessProbe:              # pronto para receber tráfego?
            httpGet: { path: /, port: 80 }
          livenessProbe:               # está vivo? se falhar, o kubelet reinicia
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 10
          resources:
            requests: { cpu: 50m, memory: 64Mi }   # o que o scheduler reserva
            limits: { memory: 128Mi }              # passou disso, o container é morto (OOMKilled)
```

Requisitos do Deployment `app`, que o check confere:

- 2 réplicas
- imagem `trilha-app:<tag fixa>` com `imagePullPolicy: IfNotPresent`
- `readinessProbe` em `/health` e uma `livenessProbe`
- `requests.cpu` e `limits.memory`
- `APP_VERSION` e `PORT` vindos do ConfigMap `app` (via `envFrom`)
- `DATABASE_URL` vindo do Secret `db` (via `secretKeyRef`)

No Secret, use `stringData` em vez de `data`, para não ter que codificar em base64 na mão. A `DATABASE_URL` aponta para o Service do banco: `postgres://trilha:trilha@db:5432/trilha`.

!!! note "Banco no cluster com `emptyDir`"
    Para estudo, monte o volume de dados do Postgres com `emptyDir: {}`. Ou seja, os dados morrem junto com o pod. Em produção você usaria um PersistentVolumeClaim, ou, mais comum, um banco gerenciado fora do cluster.

```bash
kubectl apply -f projeto/k8s/
kubectl -n trilha rollout status deploy/app
kubectl -n trilha get pods -w             # acompanhe até READY 1/1 (Ctrl+C sai)
kubectl -n trilha port-forward svc/app 8080:80
curl localhost:8080/health                # em outro terminal
```

### Rollout e rollback

```bash
kubectl -n trilha set image deploy/app app=trilha-app:0.1.1   # ou edite o YAML e rode apply
kubectl -n trilha rollout status deploy/app
kubectl -n trilha rollout history deploy/app
kubectl -n trilha rollout undo deploy/app                     # volta para a versão anterior
```

Mudanças feitas com `set image` ou `edit` **não ficam no git**. O manifest no repo é a verdade, então atualize-o também.

## 6. Debug: o roteiro

Quando um pod não fica `Running` e `READY 1/1`, siga este roteiro:

1. `kubectl get pods`: qual é o **STATUS**?
2. `kubectl describe pod NOME`: leia os **Events** de baixo para cima.
3. `kubectl logs NOME` (e `--previous` se ele reiniciou).

| STATUS / evento | Causa típica |
|---|---|
| `ErrImagePull`, `ImagePullBackOff` | Imagem ou tag não existe, ou é local e não foi importada |
| `CrashLoopBackOff` | O processo sobe e morre. Veja os logs com `--previous` |
| `Pending` | Faltam recursos no node, ou há um PVC sem volume. Veja os Events |
| `Running` mas `READY 0/1` | A `readinessProbe` está falhando (rota ou porta erradas, app lenta) |
| `OOMKilled` | Passou do `limits.memory` |
| `CreateContainerConfigError` | ConfigMap ou Secret referenciado não existe, ou a chave está errada |
